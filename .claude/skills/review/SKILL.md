# コードレビュー

現在のブランチで base ブランチ（main）から加えた変更差分を対象にレビューしてください。

## 1. レビュー対象の特定

```bash
git fetch origin main
git diff origin/main...HEAD
git diff origin/main...HEAD --name-only
```

- コミット済み差分に加え、ワーキングツリーの未コミット変更（`git status` / `git diff` / `git diff --staged`）があれば対象に含める
- 差分が存在しない場合はその旨を報告してレビューを終了する

## 2. コーディング規約への準拠確認

`.claude/rules/coding.md` と README.md の「コーディング規約」「設計方針」セクションを読み、差分がこれらに準拠しているか確認する。主なチェック項目:

- 命名: 変数・メソッドは camelCase、テーブル名・カラム名は snake_case、Controller は単数形 + Controller
- バリデーションは Form Request（`app/Http/Requests/`）を使っているか。Controller に `$request->validate()` を直接書いていないか
- Controller が肥大化していないか。複数モデルにまたがる処理・複雑なロジックは `app/Services/` の Service クラスに切り出されているか
- アクセス制御は Policy で実装し、Controller で `$this->authorize()` を呼んでいるか。Policy が `AuthServiceProvider` に登録されているか
- モデルのリレーションが明示的に定義されているか
- 重要なドメインイベントが Event/Listener パターンで実装されているか
- Blade 画面のエラー処理がリダイレクト + フラッシュメッセージになっているか

既存コードに規約未準拠の箇所（例: `CoachCourseController::store` の肥大化）があっても、それをそのまま新規・改修コードに引き継いでいないか確認する。

## 3. テストの有無確認

- 変更内容に対応する Feature テストが `tests/Feature/` に追加・更新されているか確認する
- 新機能・バグ修正に対してテストが欠けている場合は指摘する
- テストメソッド名が `test_` プレフィックスになっているか確認する
- 可能であれば実際にテストを実行して結果を確認する

```bash
./vendor/bin/sail artisan test
```

## 4. セキュリティ上の問題確認

Laravel/PHP の観点から以下を確認する:

- Mass assignment: `$request->all()` を `create()` / `update()` / `fill()` に直接渡していないか。`$fillable` / `$guarded` が適切か
- 認可漏れ: 変更対象のリソースに Policy・`$this->authorize()` が実装されているか（admin / coach / student のロール境界を侵害していないか）
- SQL インジェクション: 生クエリでの文字列結合（`DB::raw()` や変数埋め込み）がないか。バインディングを使っているか
- XSS: Blade で `{!! !!}` を使いユーザー入力をエスケープせず出力していないか
- CSRF: 新規フォームに `@csrf` が入っているか
- 認証漏れ: 保護すべきルートに `auth` ミドルウェアが付いているか
- 機密情報: API キー・パスワード等のハードコードや `.env` の値のコミットがないか
- ファイルアップロード: 拡張子・MIME タイプ・サイズの検証があるか

## 5. 不要なデバッグコードの検出

差分に以下のパターンが残っていないか検索する。

```bash
git diff origin/main...HEAD | grep -nE '^\+.*(dd\(|dump\(|var_dump\(|print_r\(|ray\(|console\.log\(|debugger;)'
```

- `dd()`, `dump()`, `var_dump()`, `print_r()`, `ray()` などの PHP デバッグ関数
- `console.log()`, `debugger;` などの JS デバッグコード
- コメントアウトされた古いコードの残骸
- 一時的に追加された `Log::debug()` / `Log::info()`（意図した運用ログか確認する）

## 6. 結果の報告

指摘事項を重大度「必須修正」→「推奨修正」→「問題なし」の順に、各重大度の中をカテゴリ別（規約違反／テスト不足／セキュリティ／その他）にまとめて報告する。各指摘には該当ファイル・行番号を `file:line` 形式で付す。

### 重大度の基準

- **必須修正**: マージ前に対応すべき問題。セキュリティ上の脆弱性、認可・ロール境界の破り、不要なデバッグコードの混入、挙動やセキュリティに影響する規約違反など
- **推奨修正**: 対応が望ましいが必須ではない問題。軽微な規約逸脱（命名規則など）、不足しているテスト、保守性に関する指摘など
- **問題なし**: 該当カテゴリで指摘事項が見つからなかった場合

### 出力フォーマット

```markdown
## コードレビュー結果

### 必須修正
#### 規約違反
- file:line - 説明（該当なしの場合は「該当なし」）

#### テスト不足
- file:line - 説明（該当なしの場合は「該当なし」）

#### セキュリティ
- file:line - 説明（該当なしの場合は「該当なし」）

#### その他
- file:line - 説明（該当なしの場合は「該当なし」）

### 推奨修正
#### 規約違反
- file:line - 説明（該当なしの場合は「該当なし」）

#### テスト不足
- file:line - 説明（該当なしの場合は「該当なし」）

#### セキュリティ
- file:line - 説明（該当なしの場合は「該当なし」）

#### その他
- file:line - 説明（該当なしの場合は「該当なし」）

### 問題なし
- 必須修正・推奨修正のいずれにも該当しなかったカテゴリを列挙する（例: 「テスト不足: 問題なし」）
```

- 必須修正・推奨修正の各カテゴリ見出しは省略せず、該当する指摘がなければ「該当なし」と明記する
- 同じカテゴリ内で必須修正・推奨修正の両方に該当する指摘がある場合は、それぞれのセクションに分けて記載する
- このレビューでは指摘のみ行い、コードの修正は行わない（修正はユーザーの別途の指示があってから行う）
